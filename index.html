ARQUITECTOS NoSQL

Una empresa, cuatro modelos

EQUIPO D · NEO4J
📚 Administración de Bases de Datos 🎓 Ingeniería de Sistemas 🗄️ Modelo orientado a grafos
Objetivo: Analizar y justificar la selección de una tecnología NoSQL según las necesidades de una plataforma digital, identificando las ventajas, limitaciones y características del modelo de grafos mediante Neo4j.

1 Problema

La empresa desarrolla una plataforma digital similar a MercadoLibre e Instagram, que necesita administrar productos, usuarios, compras, seguidores, reseñas y recomendaciones.

Después de los cambios en los requisitos, el principal problema identificado para nuestro equipo es la necesidad de administrar y analizar relaciones complejas entre usuarios, permitiendo encontrar amigos de amigos hasta cuatro niveles y generar recomendaciones de productos según las conexiones y comportamientos de los usuarios.

El sistema debe identificar cómo se relacionan los usuarios, qué productos compran, qué personas siguen y qué intereses comparten.

2 Modelo seleccionado

◉

Neo4j – Modelo de grafos

Base de datos NoSQL orientada al almacenamiento y procesamiento de relaciones entre entidades.

MODELO RECOMENDADO

Seleccionamos Neo4j porque permite representar información mediante nodos, relaciones y propiedades.

  • Nodos: representan entidades como usuarios, productos y compras.
  • Relaciones: representan conexiones como seguir, comprar o recomendar.
  • Propiedades: almacenan características de los nodos y relaciones.

Este modelo permite consultar conexiones directas e indirectas sin tener que realizar múltiples uniones entre tablas.

3 Representación

Para representar la plataforma se propone un grafo donde los usuarios, productos y compras se conectan mediante relaciones que describen sus interacciones.

Representación conceptual de entidades y relaciones.

Ejemplo de representación técnica utilizando el lenguaje Cypher:

CREACIÓN DE NODOS Y RELACIONES Cypher 
// Crear usuarios
CREATE (u1:Usuario {
    id: 101,
    nombre: "Carlos"
});

CREATE (u2:Usuario {
    id: 102,
    nombre: "Andres"
});

CREATE (u3:Usuario {
    id: 103,
    nombre: "Laura"
});

// Crear producto
CREATE (p:Producto {
    id: 201,
    nombre: "Portatil"
});

// Crear relaciones
MATCH (u1:Usuario {id: 101}),
      (u2:Usuario {id: 102}),
      (u3:Usuario {id: 103}),
      (p:Producto {id: 201})

CREATE (u1)-[:SIGUE]->(u2),
       (u2)-[:SIGUE]->(u3),
       (u1)-[:COMPRO]->(p);

En este ejemplo, Carlos sigue a Andrés, Andrés sigue a Laura y Carlos compra un portátil.

4 Consulta principal

El requisito más importante es encontrar amigos de amigos hasta cuatro niveles de profundidad.

BÚSQUEDA DE AMIGOS HASTA CUATRO NIVELES Cypher 
MATCH (u:Usuario {id: 101})-[:SIGUE*1..4]->(amigo)
RETURN DISTINCT amigo.id, amigo.nombre;

Explicación de la consulta:

  • MATCH: busca patrones dentro del grafo.
  • Usuario {id: 101}: identifica al usuario inicial.
  • [:SIGUE*1..4]: recorre relaciones de uno a cuatro niveles.
  • amigo: representa los usuarios encontrados.
  • RETURN DISTINCT: devuelve los resultados sin duplicados.

También se pueden generar recomendaciones mediante las relaciones de compra.

RECOMENDACIÓN DE PRODUCTOS Cypher 
MATCH (u:Usuario {id: 101})-[:COMPRO]->(:Producto)
      <-[:COMPRO]-(otro:Usuario)
      -[:COMPRO]->(recomendado:Producto)

WHERE NOT EXISTS {
    MATCH (u)-[:COMPRO]->(recomendado)
}

RETURN DISTINCT recomendado.nombre;

Esta consulta identifica productos comprados por otros usuarios que comparten productos comprados con el usuario inicial, excluyendo aquellos que ya compró.

5 Ventaja y limitación

✓ Principal ventaja

Su capacidad para representar y consultar relaciones complejas de manera natural y eficiente.

  • Encontrar amigos de amigos hasta cuatro niveles.
  • Identificar conexiones entre usuarios.
  • Analizar comportamientos de compra.
  • Generar recomendaciones basadas en relaciones.
  • Identificar patrones de interacción social.

⚠ Principal limitación

Neo4j no es la mejor alternativa para almacenar grandes cantidades de datos independientes o temporales.

  • Millones de sesiones temporales.
  • Miles de millones de lecturas IoT.
  • Eventos masivos independientes.

Su rendimiento depende del diseño del grafo, los índices y la cantidad de relaciones que deban recorrerse.

7 Justificación

¿Por qué seleccionamos Neo4j?

Seleccionamos Neo4j porque los requisitos relacionados con la red social y las recomendaciones necesitan analizar conexiones entre diferentes entidades.

Aunque MongoDB permite almacenar usuarios y seguidores, Redis puede administrar relaciones mediante conjuntos y Cassandra puede almacenar registros de conexiones, ninguna de estas tecnologías tiene como especialidad recorrer relaciones de múltiples niveles como lo hace un modelo de grafos.

Comparación con las otras tecnologías

Tecnología Modelo ¿Por qué no seleccionarla para este problema?
MongoDB Documental Su modelo documental es flexible, pero las consultas de relaciones de varios niveles requieren mayor complejidad.
Redis Clave-valor Está especializado en operaciones rápidas mediante claves y estructuras de datos, no en recorridos complejos de grafos.
Cassandra Columnas anchas Está diseñado para grandes volúmenes de información distribuida y consultas previamente definidas, no para explorar relaciones variables entre usuarios.
Neo4j Grafos Seleccionado por su especialización en relaciones complejas.

+ Arquitectura recomendada

Reconocemos que no existe una tecnología NoSQL que resuelva eficientemente todos los requerimientos. Por eso proponemos una arquitectura políglota que combine las cuatro tecnologías.

Necesidad Tecnología Justificación
Catálogo heterogéneo MongoDB Flexibilidad en los atributos de los productos.
50 millones de sesiones Redis Acceso rápido y expiración automática.
Red social Neo4j Recorrido de relaciones de hasta cuatro niveles.
2.000 millones de lecturas IoT Cassandra Almacenamiento distribuido y escrituras masivas.
Carrito de compras Redis Actualizaciones rápidas de productos y cantidades.
Recomendaciones Neo4j Análisis de relaciones entre usuarios y productos.

Conclusión

Neo4j es la mejor elección para las necesidades de red social y recomendaciones de la empresa. Sin embargo, reconocemos que no existe una tecnología NoSQL que resuelva eficientemente todos los requerimientos.

Por eso proponemos una arquitectura políglota que combine MongoDB, Redis, Cassandra y Neo4j, aprovechando las fortalezas de cada modelo de almacenamiento.

La selección de una base de datos debe responder a las características de los datos, los patrones de consulta, el rendimiento y la escalabilidad que requiere el negocio.

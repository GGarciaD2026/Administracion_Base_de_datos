Arquitectos NoSQL

Una empresa, cuatro modelos: propuesta de arquitectura para una plataforma que integra comercio electrónico, red social y dispositivos IoT.

1. Problema

La empresa desarrolla una plataforma digital similar a MercadoLibre + Instagram + un sistema de logística IoT. Debe gestionar productos, usuarios, carritos, sesiones, seguidores, reseñas, recomendaciones, clicks y lecturas de sensores.

Durante el diseño, el cliente establece cuatro requisitos de alta demanda:

  • Encontrar amigos de amigos hasta cuatro niveles de profundidad.
  • Almacenar 50 millones de sesiones temporales.
  • Administrar productos cuyos atributos cambian según la categoría.
  • Guardar 2.000 millones de lecturas IoT distribuidas.

El reto consiste en seleccionar el modelo NoSQL que mejor responda a cada patrón de datos y consulta. No se debe asumir que una sola tecnología es la mejor para todas las necesidades.

2. Modelos NoSQL evaluados

Cada modelo tiene una unidad de almacenamiento y un patrón de acceso característico.

Documental

MongoDB

Unidad: documento BSON dentro de una colección.

Uso destacado: productos y perfiles con atributos variables.

Fortaleza: flexibilidad de estructura y consultas por campos.

Clave-valor

Redis

Unidad: clave asociada a un valor o estructura de datos.

Uso destacado: sesiones, caché y carritos.

Fortaleza: acceso de baja latencia y expiración TTL.

Columnas anchas

Apache Cassandra

Unidad: fila identificada por una clave primaria y organizada en particiones.

Uso destacado: eventos y telemetría distribuida.

Fortaleza: escrituras distribuidas y escalabilidad horizontal.

Grafos

Neo4j

Unidad: nodos, relaciones y propiedades.

Uso destacado: redes sociales y recomendaciones basadas en relaciones.

Fortaleza: recorridos de conexiones entre entidades.

3–7. Desarrollo de las necesidades

Cada ficha desarrolla los cinco componentes técnicos solicitados: modelo seleccionado, representación, consulta principal, ventaja, limitación y justificación.

Modelo recomendado: MongoDB

Necesidad 1. Catálogo heterogéneo

Documental
1. Problema

La tienda vende productos de distintas categorías. Un computador requiere procesador y memoria RAM; un celular requiere cámara y batería; una prenda requiere talla, color y material. Los atributos no son iguales para todos los productos.

2. Modelo seleccionado

MongoDB – modelo documental.

3. Representación 
db.productos.insertMany([
  {
    nombre: "Portátil",
    categoria: "Computadores",
    atributos: {
      procesador: "Intel i7",
      ram: "16 GB",
      almacenamiento: "512 GB SSD"
    }
  },
  {
    nombre: "Camiseta",
    categoria: "Ropa",
    atributos: {
      talla: "M",
      color: "Negro",
      material: "Algodón"
    }
  }
]);
4. Consulta principal

Buscar productos de una categoría por uno de sus atributos específicos.

db.productos.find({
  categoria: "Computadores",
  "atributos.ram": "16 GB"
});
5. Ventaja

Permite que cada documento tenga atributos diferentes, facilita ampliar el catálogo y consultar los campos que interesan sin imponer una estructura idéntica a todas las categorías.

6. Limitación

La flexibilidad exige controlar la calidad y consistencia de los datos. Si se repite información en muchos documentos, mantenerla actualizada puede ser más difícil.

7. Justificación y descarte de alternativas

MongoDB es la opción más natural porque el problema central es la variabilidad de atributos dentro de un catálogo.

  • Redis: está optimizado para recuperar valores por clave; no es la mejor opción para búsquedas flexibles por numerosos atributos.
  • Cassandra: exige diseñar tablas según consultas previstas y no ofrece la misma flexibilidad documental.
  • Neo4j: podría modelar productos como nodos, pero las relaciones no son la necesidad principal del catálogo.

Trade-off: se gana flexibilidad de esquema, pero se debe invertir en validación de documentos, índices y control de duplicación.

Modelo recomendado: Redis

Necesidad 2. 50 millones de sesiones temporales

Clave-valor
1. Problema

La plataforma debe mantener hasta 50 millones de sesiones temporales, consultarlas rápidamente y eliminar automáticamente aquellas que hayan vencido.

2. Modelo seleccionado

Redis – modelo clave-valor.

3. Representación

Cada sesión se identifica con una clave única. El valor puede contener un identificador de usuario, token o datos de sesión. En producción deben protegerse los tokens y evitar almacenar secretos en texto plano.

SET sesion:101 "datos_de_sesion" EX 3600

GET sesion:101
TTL sesion:101
4. Consulta principal

Recuperar una sesión mediante su clave y consultar su tiempo restante de vida.

GET sesion:101
TTL sesion:101
5. Ventaja

Acceso de baja latencia, estructuras de datos útiles para estados temporales y expiración automática mediante TTL.

6. Limitación

El almacenamiento en memoria puede ser costoso. Cincuenta millones de sesiones requieren calcular la memoria real, la sobrecarga, la replicación y la capacidad del clúster.

7. Justificación y descarte de alternativas

Redis encaja con un patrón de lectura y actualización frecuente por identificador, con vencimiento automático.

  • MongoDB: puede usar índices TTL, pero no está centrado en el acceso en memoria de baja latencia.
  • Cassandra: también admite TTL y distribución, pero añade complejidad para un acceso principalmente por clave.
  • Neo4j: las sesiones no necesitan recorridos de relaciones ni consultas de grafos.

Trade-off: se obtiene velocidad y expiración sencilla, a cambio de dimensionar memoria, persistencia, replicación y recuperación ante fallos.

Decisión de capacidad: no se puede asegurar que 50 millones de sesiones quepan en un clúster sin conocer el tamaño promedio de cada sesión y la memoria disponible. Se debe realizar una estimación y una prueba de carga.
Modelo recomendado: Neo4j

Necesidad 3. Red social: amigos de amigos hasta cuatro niveles

Grafos
1. Problema

La plataforma necesita encontrar usuarios conectados directa o indirectamente con una persona, recorriendo relaciones de uno a cuatro niveles.

2. Modelo seleccionado

Neo4j – modelo de grafos.

3. Representación

Los usuarios son nodos y las relaciones de seguimiento o amistad son aristas dirigidas. Si la amistad es mutua, se debe representar y consultar la reciprocidad según las reglas del negocio.

CREATE (ana:Usuario {id: 1, nombre: "Ana"})
CREATE (luis:Usuario {id: 2, nombre: "Luis"})
CREATE (maria:Usuario {id: 3, nombre: "María"})
CREATE (ana)-[:SIGUE]->(luis)
CREATE (luis)-[:SIGUE]->(maria);
4. Consulta principal

Encontrar usuarios alcanzables desde el usuario inicial siguiendo entre uno y cuatro vínculos.

MATCH (u:Usuario {id: 1})-[:SIGUE*1..4]->(amigo:Usuario)
WHERE amigo.id <> u.id
RETURN DISTINCT amigo.nombre;
5. Ventaja

Las relaciones son elementos centrales del modelo. Neo4j facilita recorrer conexiones de varios niveles y descubrir patrones de redes sociales.

6. Limitación

No es la opción más adecuada para almacenar de manera masiva eventos independientes o datos temporales de alta frecuencia. El rendimiento depende del tamaño y diseño del grafo y de la profundidad del recorrido.

7. Justificación y descarte de alternativas

Neo4j representa directamente el problema como un conjunto de usuarios conectados por relaciones y permite consultar caminos de longitud variable.

  • MongoDB: puede guardar listas de seguidores, pero recorrer niveles sucesivos requiere operaciones adicionales y puede complicarse al crecer la red.
  • Redis: puede guardar conexiones en conjuntos, pero la lógica de recorrido debe construirse en la aplicación.
  • Cassandra: es más adecuada para consultas previamente modeladas que para explorar relaciones de profundidad variable.

Trade-off: se simplifican los recorridos de relaciones, pero se debe controlar la expansión del grafo, los índices y la profundidad de búsqueda.

Modelo recomendado: Cassandra

Necesidad 4. Dos mil millones de lecturas IoT distribuidas

Columnas anchas
1. Problema

Los sensores logísticos generan 2.000 millones de lecturas con identificador de sensor, fecha, temperatura, ubicación y estado. La plataforma necesita distribuir las escrituras y consultar datos por sensor y periodo.

2. Modelo seleccionado

Apache Cassandra – modelo de columnas anchas.

3. Representación

La tabla se diseña alrededor de la consulta principal. Se incluye un segmento temporal en la clave de partición para evitar particiones ilimitadas por sensor.

CREATE TABLE lecturas_iot (
  sensor_id UUID,
  dia DATE,
  fecha TIMESTAMP,
  temperatura DECIMAL,
  ubicacion TEXT,
  estado TEXT,
  PRIMARY KEY ((sensor_id, dia), fecha)
) WITH CLUSTERING ORDER BY (fecha DESC);
4. Consulta principal

Consultar las lecturas de un sensor en un día determinado.

SELECT *
FROM lecturas_iot
WHERE sensor_id = 00000000-0000-0000-0000-000000000001
  AND dia = '2026-11-03';
5. Ventaja

Distribuye datos entre nodos, permite escrituras de alto volumen y ofrece una arquitectura diseñada para disponibilidad y escalabilidad horizontal.

6. Limitación

No está pensada para consultas ad hoc ni uniones complejas. La clave de partición y el diseño de tablas deben responder a las consultas previstas.

7. Justificación y descarte de alternativas

Cassandra es adecuada para escrituras distribuidas y consultas por claves de partición, sensor y ventana temporal.

  • MongoDB: también puede almacenar telemetría a gran escala y es una alternativa válida; Cassandra se prioriza aquí por el patrón distribuido de escrituras y consultas modeladas.
  • Redis: mantener dos mil millones de registros en memoria puede ser costoso y no es su uso principal como repositorio histórico masivo.
  • Neo4j: las lecturas son eventos temporales independientes; no requieren representar relaciones como un grafo.

Trade-off: se obtiene escalabilidad para grandes volúmenes, a cambio de diseñar cuidadosamente las particiones, la retención y las consultas.

Consideración de diseño: el tamaño de cada partición debe mantenerse controlado. El agrupamiento por día es un ejemplo; el intervalo real (hora, día u otro) debe definirse según la tasa de lecturas por sensor.
Modelo recomendado: Redis

Necesidad 5. Carrito de compras

Clave-valor
1. Problema

El usuario debe agregar productos, cambiar cantidades, consultar el contenido y retirar artículos antes de confirmar la compra.

2. Modelo seleccionado

Redis – modelo clave-valor con estructura hash.

3. Representación

Se utiliza una clave por carrito y un hash donde cada campo identifica un producto y su valor representa la cantidad.

HSET carrito:101 producto:201 2
HSET carrito:101 producto:202 1

HGETALL carrito:101
4. Consulta principal

Consultar el carrito y modificar sus artículos.

HGETALL carrito:101
HSET carrito:101 producto:201 3
HDEL carrito:101 producto:202
5. Ventaja

Permite actualizar el estado del carrito con operaciones sencillas y rápidas. También se puede establecer una expiración para carritos abandonados.

6. Limitación

Se debe gestionar la persistencia, la recuperación de datos y la sincronización con el proceso de compra. El carrito no debe considerarse por sí solo el registro contable definitivo de una orden.

7. Justificación y descarte de alternativas

Redis se recomienda cuando el carrito es un estado de trabajo que cambia con frecuencia y se consulta por usuario.

  • MongoDB: es una alternativa válida si se prioriza guardar carritos como documentos persistentes y consultar estructuras más complejas.
  • Cassandra: puede almacenar carritos, pero su diseño de tablas para consultas específicas puede ser más complejo para este caso.
  • Neo4j: el carrito no requiere analizar relaciones de varios niveles; un grafo añadiría complejidad innecesaria.

Trade-off: se prioriza velocidad de interacción, pero se necesita una estrategia para persistir y confirmar la compra de forma confiable.

Modelo recomendado: Neo4j

Necesidad 6. Recomendaciones de productos

Grafos
1. Problema

La plataforma quiere recomendar productos a un usuario a partir de productos comprados por personas con intereses o comportamientos similares.

2. Modelo seleccionado

Neo4j – modelo de grafos.

3. Representación

Se modelan usuarios, compras y productos como nodos conectados por relaciones. Por ejemplo, un usuario realiza una compra y una compra incluye productos.

CREATE (u:Usuario {id: 101})
CREATE (otro:Usuario {id: 102})
CREATE (p:Producto {id: 201, nombre: "Portátil"})
CREATE (c:Compra {id: 5001})

CREATE (u)-[:REALIZO]->(c)
CREATE (c)-[:INCLUYE]->(p)
CREATE (otro)-[:COMPRO]->(p);
4. Consulta principal

Ejemplo simplificado: recomendar productos comprados por otros usuarios que también compraron productos del usuario consultado, excluyendo los que ya tiene.

MATCH (u:Usuario {id: 101})-[:REALIZO]->(:Compra)
      -[:INCLUYE]->(compartido:Producto)
      <-[:INCLUYE]-(:Compra)<-[:REALIZO]-(otro:Usuario)
MATCH (otro)-[:REALIZO]->(:Compra)-[:INCLUYE]->(recomendado:Producto)
WHERE NOT EXISTS {
  MATCH (u)-[:REALIZO]->(:Compra)-[:INCLUYE]->(recomendado)
}
RETURN recomendado.nombre, count(*) AS afinidad
ORDER BY afinidad DESC
LIMIT 10;
5. Ventaja

Permite descubrir conexiones entre usuarios y productos, recorrer relaciones y construir recomendaciones explicables a partir de patrones de compra compartidos.

6. Limitación

El rendimiento depende del tamaño del grafo, la densidad de relaciones y el diseño de las consultas. No reemplaza necesariamente motores especializados de aprendizaje automático o ranking a gran escala.

7. Justificación y descarte de alternativas

Neo4j resulta apropiado cuando las recomendaciones dependen de conexiones entre usuarios, compras y productos.

  • MongoDB: puede guardar perfiles, historial y recomendaciones calculadas, pero explorar relaciones indirectas es menos natural.
  • Redis: es excelente para almacenar y entregar rápidamente recomendaciones ya calculadas, pero no es la primera opción para descubrir relaciones complejas.
  • Cassandra: puede guardar historiales y resultados precalculados, pero no está orientada a recorridos de grafos.

Trade-off: se facilita descubrir relaciones y patrones, pero puede ser conveniente combinar Neo4j con Redis para almacenar en caché los resultados más consultados.

Pregunta final: ¿por qué NO seleccionar las otras tres tecnologías?

El comité no debe limitarse a decir que una tecnología es buena. Debe explicar qué se gana y qué se sacrifica al seleccionarla, y por qué las alternativas no son las primeras opciones para ese requisito.

Trade-offs que deben quedar explícitos

  • MongoDB: flexibilidad documental a cambio de que las relaciones profundas requieren más trabajo de modelado o consultas adicionales.
  • Redis: baja latencia a cambio de una planificación cuidadosa de memoria, persistencia y capacidad.
  • Cassandra: distribución y escritura masiva a cambio de modelar las tablas para consultas concretas y administrar particiones.
  • Neo4j: recorridos eficientes de relaciones a cambio de que no sea la opción principal para eventos independientes o datos temporales masivos.

Preguntas para la defensa

  1. ¿Qué patrón de consulta determinó la selección?
  2. ¿Qué ventaja concreta se obtiene con el modelo elegido?
  3. ¿Qué limitación o costo se acepta?
  4. ¿Por qué cada una de las otras tres tecnologías sería menos conveniente como primera opción?
  5. ¿En qué caso una de las alternativas descartadas sí podría ser una opción válida?

Conclusión

La selección de una base de datos NoSQL debe partir de la naturaleza de los datos, el volumen, la velocidad de escritura, la estructura de las relaciones y las consultas que ejecutará la aplicación.

MongoDB, Redis, Cassandra y Neo4j resuelven problemas distintos. La arquitectura propuesta combina sus fortalezas en lugar de forzar todas las necesidades dentro de un solo motor.

La decisión de un arquitecto de bases de datos no consiste en elegir una tecnología universal, sino en justificar técnicamente cuál es la más conveniente para cada necesidad y reconocer los compromisos de esa elección.
